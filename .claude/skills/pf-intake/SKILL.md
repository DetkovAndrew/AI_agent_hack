# Постановка задачи

Методика: `knowledge/methods/problem-framing.md`.

1. Прочитай запрос PM и всё в `inbox/` (бегло — только чтобы понять контекст).
2. Сформулируй черновик постановки **сам** и покажи PM на подтверждение одним блоком:
   - Решение, которое нужно принять (а не тема): «Продолжать ли X / как изменить Y…»
   - Цель и метрика успеха; получатель результата (кто будет читать и решать)
   - Ограничения (срок, бюджет, технологии, бренд, регуляторика)
   - Доступные данные; разрешённые источники (по умолчанию: открытые сайты + файлы PM)
   - Критерии выбора варианта (что важнее: рост, маржа, риск, скорость)
2а. Выбери глубину (AGENTS.md, раздел 3а) и предложи её в том же блоке: «быстрый ответ за
   один проход или полный разбор по документам». По умолчанию — `quick`; `full` — по условиям
   из AGENTS.md (раздел 3а). Запиши `pf.py set brief.depth quick|full`.
   **В быстром режиме** дальше иди по разделу «Быстрый режим» ниже, а не по этапам.
3. Задай **только** недостающее, что меняет следующий шаг — максимум 5 вопросов, к каждому
   свой вариант по умолчанию. Используй AskUserQuestion, если доступен.
4. Запиши ответы — удобнее одним `pf.py batch analysis/brief_batch.txt`, по строке на команду:
   ```
   set brief.question "..."
   set brief.goal "..."
   set brief.recipient "..."
   set brief.constraints "..." --append      # по одному
   set brief.available_data "..." --append
   set brief.allowed_sources "*.ru" --append # или конкретные домены / open-web
   set brief.decision_criteria "..." --append
   ```
   Что PM не знает — `pf.py claim add "..." --kind assumption`.
5. Ключевые вопросы (3–7), каждый — такой, ответ на который **меняет выбор варианта**:
   `pf.py question add "..." --why "если да → вариант A, если нет → B"`.
   Обязательно включи вопрос о том, стоит ли вообще продолжать направление.
6. `pf.py stage collect --next "Загрузить файлы из inbox и найти источники по Q001–Q00N"`.

## Быстрый режим (`brief.depth = quick`)
1. Ответ PM на постановку не жди, если вопросов нет: запиши допущения и иди дальше.
2. **Сначала ключевые вопросы** (`question add`), потом поиск. Материалы — `pf.py ingest`.
   Веб — **по 1–2 поиска на каждый ключевой вопрос**, из каждого поиска скачивай 2–3 лучших
   результата; число страниц — по `brief.breadth` (narrow 3–4, normal 6–10, wide 12–20), разных типов: первоисточник (сайт/условия/отчёт компании), СМИ, отраслевая
   аналитика, локальные данные. URL бери только из результатов поиска — не угадывай.
   В Claude Code поиск по ключевым вопросам раздай субагентам `researcher` параллельно
   (по одному на вопрос); в других средах — по очереди сам.
2б. Из каждой скачанной страницы бери **все** факты, относящиеся к ключевым вопросам (обычно
   2–5), а не один: цифры, условия, даты, результаты. Рутину отдавай `source-extractor` (Haiku).
3. Ключевые утверждения и пробелы — одним `pf.py batch analysis/registry_batch.txt`.
4. Расчёты — один скрипт в `analysis/` с разделом «Устойчивость» в `_result.md`
   (границы периодов, база сравнения, сверка сумм — `.claude/agents/data-analyst.md`, п. 3а).
5. **Поиск опровержений.** Для 2–3 фактов, на которых держится рекомендация, — по одному поиску
   «против» («почему закрыли…», «провал…», «критика…»). Найденное — в реестр как обычно.
6. Перед написанием — **один** `pf.py digest` (весь реестр компактно) вместо серии `claim show`.
   `deliverables/summary.md` по `knowledge/templates/quick.md` пиши **одним `Write`**. У каждого ключевого вопроса —
   ответ [C] или пробел с `--q Q00N --searched "что искали"`. Допущениям и прогнозам, на которых
   стоит ответ, — порог смены рекомендации: `pf.py claim switch C0NN --range ".." --switch "при … → …"`.
7. Независимые проверки **по готовому summary.md**, каждая — в реестр проверок:
   - `red-team` (Agent, `model: sonnet`) — возражения к рекомендации;
   - `judge` (Haiku) — обещания и смысл ключевых фактов против продукта и цитат;
   - итог поиска опровержений (п. 5);
   - `fidelity` (Sonnet) — **последней**, по финальному тексту: не говорит ли документ больше,
     чем факты (анонс ≠ запуск, потерянные единицы, мнение автора, перенос на другой объект);
   `pf.py verdict add --role red-team|judge|counter|fidelity --target deliverables/summary.md --text "..."`.
   `judge` и `fidelity` запускай **параллельно** (в одном сообщении). Их замечания исправляй
   **разом** — одним `Write` нового текста, а не десятком `Edit`. Повторная проверка — только
   изменённых строк: `pf.py verdict diff --role fidelity --target deliverables/summary.md`
   → передай субагенту этот вывод, а не весь документ. **Не больше двух кругов**: полная
   проверка → исправления → проверка изменённых строк. Что осталось после второго круга —
   перечисли PM как известные ограничения, а не запускай третий круг.
   В Claude Code проверки — только субагентами (Agent): самопроверка автора не засчитывается
   при выпуске, даже если основная модель — Haiku.
8. `pf.py check --release` → исправить ошибки → `pf.py report` → `pf.py stage choice --next "PM
   подтверждает вариант или просит полный разбор"`. Отчёт и переход к выбору без пройденной
   выпускной проверки не выполняются (`--draft` — только с согласия PM, пишется в журнал).
   Покажи PM ответ, варианты и спроси подтверждение.
